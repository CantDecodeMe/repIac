Librería monolítica
Node.js + PostgreSQL

Aplicación web monolítica (Express + EJS + PostgreSQL) para gestionar el catálogo de una librería, con el modelo de datos normalizado a 4FN, CRUD completo, autenticación por rol y subida de imágenes validada.

Node.jsExpressEJSPostgreSQL4FN
01

Objetivo

El enunciado (Ejercicio-02.pdf) pedía construir una aplicación web monolítica —renderizada en el servidor, sin API REST ni intercambio de JSON entre frontend y backend— para administrar una librería en línea: libros, autores, géneros, formatos, categorías, conceptos con su definición por libro e imágenes de portada. El acceso es por cuenta registrada y un único usuario con rol Administrador gestiona todo el catálogo.

La primera parte del ejercicio consistía en redactar los requisitos (alcance, actores, requisitos funcionales y no funcionales, riesgos) antes de escribir código, y en dejar un registro de decisiones de ingeniería con el formato necesidad → alternativas → decisión → justificación → riesgo → validación.

02

Qué construí

routes/HTTPReciben la petición, validan parámetros y deciden qué vista renderizar.
→
services/Negocio + SQLÚnica capa que consulta PostgreSQL, siempre con consultas parametrizadas.
→
views/EJSPlantillas que sólo reciben datos ya procesados; sin SQL ni reglas de negocio.
  • 1

    Base de datos en 4FN. Esquema con PK/FK/UNIQUE/CHECK que reflejan las reglas del negocio (stock ≥ 0, precio > 0, ISBN único, un solo Administrador), relaciones muchos-a-muchos libro–autor y libro–género, más stored procedures, triggers y vistas propias.

  • 2

    Autenticación y autorización. Contraseñas con hash (bcrypt), sesión de servidor y middleware que restringe cada ruta /admin/* al único Administrador; un usuario regular recibe un acceso denegado controlado, no un error crudo.

  • 3

    CRUD completo sobre libros y catálogos independientes (autores, géneros, formatos, categorías, conceptos), con búsqueda por ISBN exacto y por título insensible a mayúsculas y acentos.

  • 4

    Subida de imágenes validada. Se revisa extensión, tipo MIME real y tamaño; el nombre de archivo lo genera el servidor y nunca se usa el enviado por el usuario. Una sola imagen puede marcarse como portada por libro.

  • 5

    Manejo de errores centralizado. El detalle técnico va a los logs del servidor; el usuario final siempre ve un mensaje genérico, nunca un stack trace ni el SQL ejecutado.

03

Decisiones de ingeniería

  1. A

    Monolito server-side en vez de SPA + API o microservicios: lo exige el enunciado y, para un proyecto de un solo desarrollador, reduce la complejidad operativa (un proceso, una base de código, sin contratos de API).

  2. B

    Driver pg sin ORM. Un ORM esconde el SQL y complica demostrar el modelo 4FN tal como se diseñó; con pg tengo control total del pool de conexiones y de la parametrización. El costo es más código repetitivo y disciplina manual para no concatenar strings.

  3. C

    EJS para el HTML: sintaxis cercana a HTML+JS, parciales reutilizables para navegación y formularios, y es la opción sugerida por el enunciado. El riesgo —lógica filtrándose a las vistas— se controla con la regla de que views/ sólo recibe datos ya procesados.

04

Reflexión

Lo que más me costó fue la parte de infraestructura. El enunciado asumía una VM propia en la nube con privilegios de administrador; el entorno real con el que trabajé es un servidor compartido sin acceso privilegiado. Tuve que verificar primero qué había disponible y adaptar esa parte del ejercicio sin recortar el resto del alcance (base de datos 4FN, CRUD, seguridad, pruebas). Me quedó claro que "desplegar" no es sólo subir archivos: hay que pensar en cómo se mantiene vivo un proceso, en qué puerto escucha y en cómo se aísla de otros usuarios del mismo servidor.

En el diseño de datos, llevar el esquema hasta 4FN me obligó a separar cosas que al principio había metido en la misma tabla —por ejemplo, la definición de un concepto, que cambia según el libro— y a apoyarme en restricciones de la base de datos en vez de confiar sólo en la validación de la aplicación. La separación rutas / servicios / vistas se volvió incómoda de respetar cuando tenía prisa, pero es justo lo que después hizo fácil cambiar una consulta sin tocar la interfaz.

Uso responsable de IA

La IA apoyó la redacción de requisitos, la estructura inicial del proyecto y la revisión del SQL. Las decisiones de arquitectura, el modelo de datos y los ajustes se comprendieron y validaron con casos de prueba; la responsabilidad de los resultados permaneció en el estudiante.
