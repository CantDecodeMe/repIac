Actividad 07 · Autenticación en APIs REST

¿Qué es un JWT?

Un JSON Web Token es una credencial firmada: el servidor la entrega tras el login y el cliente la presenta en cada petición. El servidor no necesita guardar sesiones; le basta comprobar la firma.

Authorization: Bearer …

Sigue bajando: el token se forma con tu scroll ↓

Anatomía

Tres partes, separadas por puntos

No está cifrado: está codificado en base64url y firmado. Cualquiera puede leerlo; solo quien tiene la clave puede fabricarlo.

Header · qué algoritmo firmó y con qué clave.

Payload · las claims: quién eres y hasta cuándo vale.

Firma · prueba de que nadie tocó las otras dos.

parte3 = HMAC-SHA256(secreto, "parte1.parte2")

                

              

            

          

        

        

          

            
Paso 1

            
Cabe en una cabecera HTTP

            
Tres cadenas de texto unidas con puntos: header.payload.firma. Al ser texto seguro para URL, viaja sin problema en Authorization.

          

          

            
Paso 2 · Header

            
Cómo se firmó

            
Decodificar es reemplazar -→+ y _→/, rellenar con = y aplicar atob. Aquí dice alg: HS256 y qué clave usar con kid.

          

          

            
Paso 3 · Payload

            
Lo que el servidor afirma

            
sub (sujeto), iat (emitido) y exp (expira), más lo que quieras añadir. Es legible por cualquiera: nunca pongas contraseñas ni datos sensibles.

          

          

            
Paso 4 · Firma

            
Lo único que no se puede falsificar

            
No es JSON: son 32 bytes (256 bits) de un HMAC. Si cambias una sola letra del header o del payload, la firma que el servidor recalcula ya no coincide.

          

        

      

    


    
    

      

        
Pruébalo

        
Decodifica y verifica en vivo

        
Edita el token (cambia una letra del payload) o pega uno tuyo. Todo ocurre en tu navegador; nada se envía a ningún servidor.

Construcción

        
Cómo se fabrica un token, paso a paso

        
Esto es exactamente lo que hace el microservicio de autenticación cuando un login es correcto. Los valores mostrados son reales, calculados en esta página.

      

      

        

          

            

              

                
1 · Se arma el JSON del header

                

                
alg algoritmo · typ tipo de token · kid identificador de la clave

              

              

                
2 · alg decide cómo se firma y cómo se verifica

                

                  
HS256 · HMAC + SHA-256 · clave compartida

                  
firma = HMAC(secreto, header.payload)

                  
Quien firma y quien verifica comparten el mismo secreto. Simple y rápido; ideal si emisor y verificador son de confianza.

                

                

                  
RS256 · RSA + SHA-256 · clave pública/privada

                

              

              

                
3 · La alternativa asimétrica

                

                  
HS256 · clave compartida

                

                

                  
RS256 · RSA + SHA-256 · clave pública/privada

                  
firma = RSA(clave privada, hash(header.payload))

                  
Solo auth-ms guarda la clave privada. Los demás servicios verifican con la pública y no pueden emitir tokens. kid indica cuál par usar al rotar claves.

                

              

              

                
4 · Header → base64url

                

                
↓ base64url

                

              

              

                
5 · Payload (claims) → base64url

                

                
↓ base64url

                

              

              

                
6 · Se firma header.payload con el secreto

                

                
Resultado: los tres textos unidos con puntos

                

              

            

          

        

        

          

            
Paso 1 · Header

            
Empieza con un JSON pequeño

            
Declara el algoritmo (alg), el tipo (typ: "JWT") y, opcionalmente, qué clave se usó (kid).

          

          

            
Paso 2 · Algoritmo

            
HS256: un secreto compartido

            
Es la opción más simple. El servidor que verifica necesita el mismo secreto con el que se firmó, así que cualquiera que pueda verificar también podría emitir.

          

          

            
Paso 3 · Algoritmo

            
RS256: privada firma, pública verifica

            
Con microservicios conviene separar poderes: solo el servicio de autenticación emite; los demás únicamente comprueban con la clave pública.

          

          

            
Paso 4 · Header

            
Se codifica en base64url

            
Los bytes del JSON pasan a un alfabeto seguro para URL (A–Z a–z 0–9 - _, sin =). Es reversible: no protege nada, solo transporta.

          

          

            
Paso 5 · Payload

            
Las claims: sub, iat y exp

            
sub identifica al usuario, iat es cuándo se emitió y exp cuándo deja de valer (segundos Unix). Se codifica igual que el header.

          

          

            
Paso 6 · Firma

            
Se sella todo y se entrega

            
Se calcula el HMAC sobre header.payload ya codificados y se agrega como tercera parte. Ese texto es el token que recibe el cliente.

          

        

      

    


    
    

      

        
El viaje

        
Un token recorre una API de microservicios

        
Mismo esquema que el curso: un servicio de autenticación (auth-ms) y otro de datos (libros-ms). Los datos de ejemplo son ficticios.

      

      

        

          

            
            

              
POST /login HTTP/1.1
Content-Type: application/json

{"email": "ana@correo.mx", "password": "••••••••"}

              
auth-ms:
1. busca al usuario y compara el hash de la contraseña  ✓
2. arma el payload  {sub, iat, exp}
3. firma  header.payload  con su clave  →  JWT

              
HTTP/1.1 200 OK

{"access_token": "eyJhbGciOi….eyJzdWIiOi….SflKxw…"}

              
cliente: guarda el token
- en memoria (más seguro, se pierde al recargar)
- o en almacenamiento del navegador / app
El servidor no guarda nada de la sesión.

              
GET /libros HTTP/1.1Host: libros.ejemplo.mxAuthorization: Bearer eyJhbGciOi…SflKxwAccept: application/json

              

                
    
                  
  • ·Recalcula la firma con la clave y compara
    • 
                  
  • ·Comprueba exp > ahora
    • 
                  
  • ·Lee sub y decide qué puede ver
    • 
                

              

              
HTTP/1.1 200 OK

[{"id": 1, "titulo": "Cien años de soledad"}, …]

            

          

        

        

          

            
Paso 1

            
El cliente pide entrar

            
Envía sus credenciales a POST /login. Es la única vez que viaja la contraseña.

          

          

            
Paso 2

            
auth-ms emite el token

            
Valida las credenciales, arma el payload y lo firma. Aquí ocurre todo lo que viste en «Construcción».

          

          

            
Paso 3

            
Responde con el JWT

            
El cuerpo de la respuesta lleva el token. Desde aquí, la contraseña ya no se vuelve a enviar.

          

          

            
Paso 4

            
El cliente lo guarda

            
Es su «pase». Quien lo tenga, es ese usuario mientras no expire: por eso hay que cuidarlo.

          

          

            
Paso 5

            
Lo presenta en cada petición

            
Va en la cabecera Authorization: Bearer <jwt> (resaltada). «Bearer» significa portador: vale quien lo porta.

          

          

            
Paso 6

            
libros-ms verifica, sin llamar a nadie

            
Comprueba firma y expiración por su cuenta. Por eso los JWT escalan bien entre microservicios: no hay consulta a una base de sesiones.

          

          

            
Paso 7

            
Responde 200 con los datos

            
Si algo falla (firma inválida, token vencido) la respuesta es 401 Unauthorized. Justo lo que veremos a continuación.

          

        

      

    


    
    

      

        
Expiración

        
Todo token caduca

        
Para la demo este token dura solo 30 segundos. En producción suelen ser de 5 a 15 minutos.

    Paso 1
    
            
    La claim exp es una fecha límite
    
            
    Es un instante en segundos Unix. El contador de la derecha resta ese valor al reloj real de tu navegador, ahora mismo.
    
          
    
          
    
            
    Paso 2
    
            
    Se revisa en cada petición
    
            
    Prueba a llamar a la API mientras corre el tiempo: responde 200. La firma sigue siendo válida; lo que cambia es el reloj.
    
          
    
          
    
            
    Paso 3
    
            
    Al llegar a 0: 401
    
            
    El token no fue alterado, pero ya no vale. El servidor lo rechaza con 401 Unauthorized y el cliente debe conseguir otro. Espera el cero o usa «Saltar».
    
          
    
        
    
      
    
    
    

    
    
    
      
    
        
    Refresco
    
        
    Seguir conectado sin volver a poner la contraseña
    
        
    Un token corto limita el daño si se filtra; pero pedir la contraseña cada 15 minutos sería insoportable. Solución: renovar la sesión. Es el mismo patrón de POST /session/extend del Ejercicio 06, aquí con un par access/refresh.
    
      
    
      
    
        
    
          
    
            
    
              
    access token · 15 min · viaja en cada petición
    
              
    
            
    
            
    
              
    refresh / sesión · 7 días · solo va a /session/extend
    
              
    
            
    
            
      
              
    • 1. Cliente usa el access token en cada llamada → 200
      • 
              
    • 2. El access token vence → 401 (el cliente lo detecta)
      • 
              
    • 3. POST /session/extend con el refresh → nuevo access token
      • 
              
    • 4. Repite la petición original con el token nuevo → 200 · el usuario ni se enteró
      • 
            
    
            
    
              
    token anterior
    
              
    token nuevo
    
            
    
          
    
        
    
        
    
          
    
            
    Paso 1
    
            
    Dos duraciones distintas
    
            
    El access token es corto y se envía por todos lados. La sesión larga solo se usa en un endpoint concreto, así casi nunca se expone.
    
          
    
          
    
            
    Paso 2
    
            
    El access token se agota
    
            
    La API contesta 401. En lugar de mandar al usuario al login, el cliente intenta renovar en silencio.
    
          
    
          
    
            
    Paso 3
    
            
    Se extiende la sesión
    
            
    El servidor valida la sesión larga y firma un token con iat y exp nuevos. Fíjate: cambian los tiempos, no el sub.
    
          
    
          
    
            
    Paso 4
    
            
    Todo sigue sin re-login
    
            
    Se reintenta la petición original y funciona. Si la sesión larga también venciera (o se revocara), ahí sí toca iniciar sesión otra vez.
    
          
    
        
    
      
    
    
    

    
    
    
      
    
        
    Seguridad
    
        
    Lo que sale mal cuando se usa mal
    
        
    Un JWT es tan seguro como la verificación que hace el servidor.
    
      
    

      
    
        
    
          
    alg: "none"
    
          
    El estándar permite tokens «sin firma». Un atacante cambia el header y borra la firma; si el servidor obedece al header, acepta cualquier payload.
    
          
    {"alg":"none","typ":"JWT"}.{"sub":"ana","role":"admin"}.
    
          
    Defensa: el servidor define una lista de algoritmos permitidos y rechaza none.
    
        
    
        
    
          
    Confusión de algoritmo
    
          
    El servidor espera RS256 (verifica con la clave pública). El atacante manda HS256 y firma usando esa clave pública —que es pública— como si fuera el secreto.
    
          
    Defensa: el algoritmo lo fija el servidor según la clave que tiene; nunca se deduce del alg del token.
    
        
    
        
    
          
    Legible, pero no modificable
    
          
    Cualquiera lee el payload, pero cambiarlo rompe la firma. Compruébalo:
    
          
    
          
    
          
    
            
            
          
    
          
    
        
    
        
    
          
    Sin HTTPS, cualquiera lo copia
    
          
    Un token Bearer vale para quien lo presente. Si viaja por HTTP plano, cualquiera en la red puede leerlo y reutilizarlo hasta que expire.
    
          
    Defensa: TLS siempre, token en la cabecera Authorization (nunca en la URL, que queda en logs) y exp corto.
